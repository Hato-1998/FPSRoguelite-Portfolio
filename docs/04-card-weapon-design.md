# 사례 03 · 데이터 기반 카드와 무기 상태의 분리

[← 포트폴리오](../README.md) · [카드 코드](../samples/card-effects.md) · [무기 코드](../samples/weapon-stats.md)

## 문제

카드는 플레이어 속성, 전체 무기 수치, 특정 무기 수치, 행동을 바꿀 수 있습니다. 이를 중앙 함수의 카드별 분기로만 처리하면 종류가 늘 때마다 같은 파일이 커집니다. 공통 무기 정의에 개인 업그레이드를 저장하면 서로 다른 플레이어의 상태도 섞입니다.

## 카드 효과를 다형적 객체로 구성한다

카드 DataAsset은 `UFPSRCardEffect` 기반 효과 목록을 갖습니다. 서버는 `FFPSRCardEffectContext`에 PlayerState·ASC·Inventory·대상 무기를 모아 효과에 전달합니다.

`ApplyCard`는 두 번 순회합니다.

1. 모든 유효 효과의 `CanApply`를 확인합니다. 하나라도 적용할 수 없으면 효과 적용 전에 거부합니다.
2. 효과별 희귀도 수치를 계산하고 `Apply`를 실행합니다. 이후 획득 카드 기록을 남깁니다.

중앙 적용 루프는 구체적인 효과 종류를 검사하지 않습니다. 새로운 효과는 기존 계약을 구현하는 파생 클래스로 확장할 수 있습니다. 다만 새로운 스탯 축이나 UI 표현까지 언제나 수정 없이 추가되는 것은 아닙니다.

**계약의 한계:** 현재 `Apply`는 실패 결과를 반환하지 않습니다. 선행 효과가 후행 효과의 전제를 깨지 않도록 해야 하며, 새로운 효과 구현은 `CanApply`의 완전성과 콜백 부작용을 검토해야 합니다. 두 단계 검사만으로 임의의 효과 조합에 대한 완전한 원자성을 보장한다고 설명하지 않습니다.

## 공유 정의와 개별 인스턴스

| 데이터 | 위치 | 변경 성격 |
|---|---|---|
| 기본 무기 수치 | `WeaponDataAsset` | 콘텐츠 저작 데이터 |
| 개인 무기의 탄약·장전 | `WeaponInstance` | 런타임 복제 상태 |
| 특정 무기 수정치 | `WeaponInstance.Modifiers` | 해당 무기에 누적 |
| 전체 무기 수정치 | `PlayerState` | 플레이어의 모든 해당 무기에 적용 |
| 발사 모드 변경 | 행동 Fragment | 수치 계산 후 동작에 반영 |
| 최종 계산 수치 | 인스턴스 캐시 | 변경 이후 다음 조회에서 재계산 |

`GetResolvedStats`는 dirty 상태일 때만 `RecomputeResolved`를 호출합니다. `OnRep_Source`, `OnRep_Modifiers`, `OnRep_ActiveFragments`는 캐시를 무효화합니다. 캐시는 복제된 입력에서 계산하며 그 자체를 복제하지 않습니다.

## 수치 합성의 규칙

기본적인 수치 합성은 `(기본값 + 가산값 합) × (1 + 비율값 합)`입니다. 이후 스탯별 제한을 적용합니다. 예를 들어 탄창 크기는 최소 1, 발사 속도는 양수, FOV는 5~170도로 제한합니다.

전체 무기 수정치에는 무기 정의의 제외 축을 적용할 수 있습니다. 특정 무기를 명시적으로 대상으로 한 수정치는 이 필터를 거치지 않습니다. 마지막으로 Fragment가 발사 모드와 점사 횟수를 바꿀 수 있습니다.

이 구조는 수치의 결합 순서를 한곳에서 설명할 수 있게 합니다. 반면 새 스탯 축을 추가할 때 `RecomputeResolved`의 switch를 함께 바꿔야 합니다. 효과 확장과 스탯 축 확장은 서로 다른 확장 지점입니다.

## 빌드 시너지의 작은 예

`ComputeSynergyMultiplier`는 카드의 태그별 누적 수를 전부 더하지 않고 가장 큰 값 하나를 고릅니다. 태그가 많은 카드가 단순히 유리해지는 편향을 줄이려는 규칙입니다. 상한을 적용한 뒤 `1 + BonusPerCard × count`로 가중 배율을 계산합니다. [함수 발췌](../samples/card-effects.md)

## 유지해야 할 검증

새 효과의 적용 불가 조건, 전체 무기 수정 후 캐시 무효화, 복제 직후의 화면 갱신, 무기별 제외 축과 스탯 제한을 검증해야 합니다. 공개본은 해당 구조를 보여 주는 코드 발췌이며 모든 경로의 테스트 통과를 주장하지 않습니다.
