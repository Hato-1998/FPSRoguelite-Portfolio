# 사례 01 · 적떼가 공유하는 길찾기와 풀

[← 포트폴리오](../README.md) · [현재 상태](08-current-state.md)

다수의 적이 공유하는 Flow Field(목표까지의 거리·진행 방향을 담은 장)와 클래스별 액터 풀을 구현한 사례입니다. 반복 탐색을 공유하고 높이·낙하·재사용의 예외를 데이터 구조에 담았습니다. 아래 구조와 과거 측정은 각각 구현 확인과 특정 조건의 실행 기록입니다.

## 문제

다수의 적이 소수의 플레이어를 추적합니다. 적마다 독립된 탐색을 반복하면 비슷한 일을 여러 번 계산하게 됩니다. 또한 경사로와 겹친 바닥이 있는 지형에서는 평면상의 같은 셀도 서로 다른 높이의 위치일 수 있습니다.

## 선택: 표면 그래프에서 공유 거리장을 계산한다

`UFPSRFlowFieldComputer`는 셀과 높이 레이어로 표면을 구분합니다. `RunBFS`는 BFS(너비 우선 탐색)로 플레이어에 대응하는 여러 표면을 시작점에 넣고, 같은 비용의 연결을 따라 거리장을 계산합니다. 각 표면의 방향은 더 작은 거리의 이웃을 향합니다. 개별 적은 계산된 결과를 샘플링합니다.

표면 수를 V, 연결 수를 E라 하면 BFS 단계는 O(V+E)입니다. 전체 재계산을 O(1)로 부르지 않습니다. 높이 레이어와 주변 탐색 범위가 고정된 개별 샘플 조회가 일정한 범위의 배열 접근이라는 점과 구분해야 합니다.

| 선택 | 얻는 것 | 감수하는 것 |
|---|---|---|
| 다중 시작점 공유 거리장 | 소수의 목표를 향한 탐색 결과 재사용 | 개별 적마다 다른 이동 비용·목표 정책을 넣기 어려움 |
| 높이 레이어를 가진 셀 | 겹친 지형의 표면을 구분 | 현재 2개 레이어의 표현 한계와 높이 선택 규칙 필요 |
| 균일 비용 BFS | 간단한 거리 계산과 검증 | 물리적 이동 시간에 대한 최적 경로를 보장하지 않음 |
| 월드 연결과 계산 객체 분리 | 합성 데이터로 회귀 테스트 가능 | 베이크 좌표계와 런타임 좌표계 변환 계약 유지 필요 |

## 단방향 낙하는 역방향 탐색이 필요하다

낭떠러지 A에서 아래 B로 내려갈 수 있어도 B에서 A로 같은 방식으로 올라갈 수는 없습니다. 목표 B에서 거꾸로 거리장을 전파할 때는 B로 떨어질 수 있는 A를 찾아야 합니다.

`RebuildDropLinks`는 허용된 낙하 높이와 착지 표면을 검사해 `DropTarget`을 만듭니다. 이어서 유입 링크를 CSR(Compressed Sparse Row: 연결 목록을 연속 배열과 시작 인덱스로 압축한 표현) 형태인 `DropInStart`와 `DropInSource`에 저장합니다. BFS가 B를 꺼내면 B로 들어오는 낙하 출발 표면만 순회합니다. 매번 전체 낙하 링크를 훑는 일을 피합니다.

```mermaid
flowchart LR
    Bake["베이크된 표면·낙하 후보"] --> Filter["착지 표면·높이 제한 검사"]
    Filter --> Out["DropTarget: A에서 B로"]
    Out --> CSR["유입 CSR: B로 들어오는 A 목록"]
    Player["플레이어 표면들"] --> BFS["다중 시작점 BFS"]
    CSR --> BFS
    BFS --> Flow["더 낮은 거리의 방향 선택"]
    Flow --> Enemy["개별 적이 샘플링"]
```

연결성 레이블과 방향장 준비 상태도 분리합니다. 플레이어 시작점을 찾지 못해 방향장이 유효하지 않아도, 지형 연결성 자체는 계산할 수 있기 때문입니다. 코드의 `bConnectivityReady`와 `bFieldReady`가 이 차이를 표현합니다.

## 정확한 클래스별 풀링

`FFPSREnemyDormantPool`은 전체 휴면 적 배열 대신 **정확한 클래스 → 해당 클래스 버킷**으로 저장합니다. 일반 적과 엘리트가 상속 관계에 있어도 서로의 요청에 잘못 반환하지 않습니다.

`AcquireOfClass`는 요청 버킷에서 뒤부터 꺼내며 무효 슬롯을 제거합니다. 해시 조회는 평균 O(1)이지만, 무효 슬롯이 이어지면 해당 버킷을 순회합니다. 따라서 취득 전체가 최악의 경우까지 O(1)인 것은 아닙니다.

총 풀 용량이 한 클래스로 채워져 다른 클래스를 만들 수 없는 경우도 고려합니다. `EvictOneFromLargestOtherBucket`은 다른 클래스 중 가장 큰 휴면 버킷에서 하나를 꺼냅니다. 실제 파괴와 총량 회계는 호출하는 스폰 서브시스템의 책임입니다. 버킷 선택은 클래스 수에 비례하고, 축출이 잦으면 풀링 이점이 줄어듭니다.

## 패키지 측정으로 확인한 병목

2026-09-17에는 UE5.8 계열의 같은 Development 패키지와 맵에서 솔로와 로컬 4인 조건을 측정했습니다. Ryzen 7 7800X3D / RTX 4070 Ti, 1080p 렌더 호스트, Push Model(변경 속성을 명시하는 복제 방식) OFF 조건입니다. 4인 구성의 나머지 세 클라이언트는 **같은 PC에서 렌더 없이 60fps로 실행**했습니다. 맵은 이후 폐기된 `L_Map_1`, 패키지는 `26_9_17_BuildTest_2`입니다. 표의 P95는 프레임 시간의 95백분위 값입니다.

| 호스트 지표 | 솔로 | 로컬 4인 |
|---|---|---|
| 분석 창 / 평균 생존 적 | 76.3초 / 895 | 233.9초 / 891 |
| 평균 프레임 / P95 | 9.40ms / 12.17ms | 18.62ms / 24.93ms |
| 게임 스레드 / GPU | 9.39ms / 3.56ms | 18.57ms / 3.87ms |

평균 GPU 시간보다 게임 스레드 시간이 프레임 시간에 가까워, 이 조건의 호스트 병목은 CPU였습니다. 일괄 처리 등을 포함한 Tickables는 4.95ms→11.07ms, 서버 액터 복제는 0→1.51ms였습니다. 이 비교는 조사할 비용을 좁혀 주지만, 인원 증가에 따른 원인을 하나로 분리한 실험이나 최적화 전후 결과는 아닙니다.

1000마리 소환 요청은 모두 전달됐지만 4인 분석 창의 생존 수는 829~956으로 감소했고 맵 하단 경계(Kill-Z)에 의한 회수 44건이 있었습니다. 따라서 **1000마리 안정 유지 성능**으로 소개하지 않습니다. 두 분석 창의 이벤트 조건도 다르며 같은 PC 클라이언트의 CPU 부하가 섞입니다. 연결당 송신 약 41KB/s에도 포화가 94% 프레임에서 기록됐고 원인은 미확정입니다. 원격 4인 환경과 현재 제품맵·빌드의 성능은 별도 측정이 필요합니다.

## 데모 마감 기간의 변화

2026-10-20부터 22일까지 스웜 경로와 적 표현에 세 가지가 바뀌었습니다. 위의 거리장·풀 구조와 2026-09-17 측정은 그대로 두고, 변경 내용과 확인 범위만 적습니다.

### 시야 직진 흐름 패스(FLOW-SPREAD-1)

현재 거리장은 균일 비용 BFS에 4방향 이웃을 쓰므로, 적이 플레이어와 같은 열에 맞춘 뒤 한 줄로 내려오는 모습이 사용자 플레이에서 확인되었습니다. 양선형 보간은 이산 방향을 섞을 뿐 직선 접근을 만들지 못합니다.

| 항목 | 내용 |
|---|---|
| 선택 | BFS 계산의 마지막 단계에 시야 패스를 추가합니다. 플레이어 표면 반경 안의 각 표면에서 격자 직선 추적으로 시야를 판정하고, 보이면 가장 가까운 시작점을 향해 방향을 직접 기록합니다 |
| 기각한 안 | 8방향 Dijkstra와 가중 평균 기울기는 구역 안에서 방향이 고정각으로 수렴해 8개 줄이 되었습니다. 벽 근접 비용은 오히려 적을 중앙으로 모읍니다. 이웃 연쇄로 시야를 정하는 안은 직선이 아님을 반례로 확인했습니다. 이 세 안은 계획 검토에서 반려되거나 손계산으로 철회했습니다 |
| 유지한 것 | 샘플링·보간·거리장·낙하 연결·연결성은 수정하지 않았습니다. 적마다 드는 비용은 늘지 않고, 계산 비용은 재계산 때 한 번 발생합니다. 기본 설정은 끔이며 끈 상태는 이전 결과와 비트 단위로 같습니다 |
| 비용 | 비용은 길이가 아니라 셀 수의 세제곱에 가깝게 늘어납니다. 데모 맵·시작점 4개 조건에서 P95는 22셀 1.0ms, 25셀 1.35ms, 30셀 2.0ms, 60셀 7ms로 측정되었습니다. 병합 전 검토에서 설정 파일로 상한을 우회할 수 있다는 지적을 받아 코드에 25셀 상한을 두었습니다 |
| 확인 | 병합 트리의 일반·비유니티 빌드 성공, FlowField 15/15, 시야 판정을 다른 알고리즘과 대조해 8,464개 표면에서 일치, 사용자 PIE에서 개선 확인(결정 DL-161) |
| 한계 | 장애물 뒤·반경 밖·선반 위층은 기존 줄 수렴이 남습니다. 문제가 되면 2단계로 유클리드 거리장(Fast Marching)을 검토합니다. 1000마리 스트레스는 실행하지 않았습니다 |

이 변경은 줄 수렴이라는 행동 문제의 수정이며 성능 개선이 아닙니다. 기존 재계산 비용(시작점 4개 조건에서 약 2.2ms)에 위 비용이 더해지므로, 추가 비용을 1.5ms 이하 예산 안에 두는 결정이었습니다.

### 적 외형을 바꾸되 복제를 늘리지 않은 선택

근접·마법사·엘리트·보스를 방향별 픽셀 스프라이트(카메라 쪽을 향하는 판)로 교체했습니다(DL-169, DL-174). 상태 표시는 기존 신호에서 각 기기가 계산하는 클라이언트 표현으로 두었습니다.

| 항목 | 내용 |
|---|---|
| 제1원리 | 스웜은 액터당 비용이 핵심이므로, 외형 상태를 적마다 복제하면 수에 비례해 대역폭이 늡니다 |
| 선택 | 일반 적은 기존 애니메이션 상태 값을 재질이 읽습니다. 보스의 7개 표시 상태(대기·추격·충전·발사·폭격 시전·등장·사망)도 보스 전환, 공격 큐의 발사 시각, 폭격 표식 같은 기존 신호로 각 기기가 계산합니다. 보스 표시를 위한 복제는 추가하지 않았습니다 |
| 예외 | 폭격 Specialist의 예고 위치는 모든 플레이어가 같은 지점을 봐야 해서, 스폰 서브시스템이 소유하는 복제 객체 하나에 목록으로 둡니다. 적마다 속성을 복제하지 않는 방식입니다(DL-170) |
| 반대 방향 변경 | 처치 코인 연출용으로 적 외형 상태에 있던 필드 6개는 코인 제거(DL-180)와 함께 서버 전용으로 돌렸습니다. 복제 크기 감소는 코드 변경 기준이며 측정하지 않았습니다 |
| 렌더 비용 | 에디터에서 같은 적 1000개를 배치한 조건의 측정 기록이 있습니다. 씬 비용이 0.2~0.7ms 늘었고 스프라이트의 BasePass는 0.06ms였으며, 같은 조건의 복셀 슬라임은 0.85~1.0ms 늘어난 기록이 있습니다. 패키지·다인·실제 런 조건의 측정이 아니므로 개선율로 해석하지 않습니다 |
| 확인 | 8방향·상태 캡처가 계약과 일치하고 자동화 71/72(실패 1건은 이번 변경 이전의 기존 시험), 사용자 PIE에서 확인했습니다 |
| 미검증 | 폭격·엘리트·보스의 2인 복제와 늦은 참가 화면은 자동 시험이 없어 미검증입니다 |

보스는 이동 방식도 바뀌었습니다. 런 맵에 내비 메시가 없어 걷는 보스가 움직이지 않는 것을 PIE에서 발견했고, 지형 위 3m 비행 추적으로 바꿨습니다. 비행은 높은 벽·건물을 돌아가지 못하는 한계가 있습니다.

### 이동 속도 조정이 추격 비율에 준 영향

DL-179에서 플레이어 이동 속도를 절반(0.5배), 적과 보스를 0.65배로 줄였습니다. 거리장은 균일 비용 BFS이고 속도를 입력으로 받지 않으므로, 이 조정은 경로 계산이 아니라 표본을 따라 움직이는 속도에만 닿습니다. 설계값 기준 적과 플레이어의 속도 비는 0.65/0.5 = 1.3배, 즉 이전보다 적이 상대적으로 30% 빨라졌습니다. 이는 설계 수치의 산술이며 추격 시간이나 피격 빈도를 측정한 기록은 없습니다. 속도 감각은 사용자 PIE로 확인했고, 세부 값은 이후 플레이로 조정하는 항목입니다.

## 검증과 한계

기존 회귀 시험은 잘못된 층 선택과 정확한 클래스 구분을 다루도록 작성되어 있습니다. 이번 문서 작업에서 시험이나 성능 측정을 새로 실행하지 않았습니다. 데모 마감 기간 절의 수치는 모두 당시 작업 기록의 값입니다. 적 1000+는 구조가 버텨야 하는 스트레스 목표이며 실제 동시 수는 Director와 예산에 따라 달라집니다.

높이 레이어 수, 베이크 해상도, 동적 장애물 반영, 낙하 연결, 네트워크 복제는 각각 별도 검증 항목입니다. 길찾기 계산 공유만으로 렌더링·충돌·복제까지 해결됐다고 볼 수 없습니다.
