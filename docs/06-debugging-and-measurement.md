## 사례 1. 패키지에서만 발생한 GC 크래시

**문제.** 데모 패키지 빌드를 사용자가 플레이하던 중 약 1분 뒤 말없이 종료됐습니다. 에디터 PIE와 헤드리스 자동화 시험은 모두 통과했습니다.

**제약.** 에디터에서는 재현되지 않고, 패키지에서만 보이는 문제라 자동화 시험이 잡을 수 없었습니다. 원인을 추측하기 전에 같은 조건에서 반복 재현되는 최소 절차가 필요했습니다.

**조사와 원인.** 크래시는 패키지의 첫 가비지 컬렉션 때 GC 가정 검증(VerifyGCAssumptions)에서 치명 오류로 났습니다. 원인은 엔진이 아니라 프로젝트 코드였습니다. 적 사망 먼지의 대체 나이아가라 시스템을 설정 클래스의 CDO(클래스 기본 객체)의 Transient 강참조에 보관했습니다. 패키지에서는 CDO가 "GC 대상에서 제외하는 풀"에 들어가는데, 그 풀의 객체가 GC 대상 객체를 강참조하면 첫 GC 검증이 실패합니다. 에디터와 헤드리스 시험은 이 검증을 하지 않아 통과했습니다.

**선택한 수정.** 로드한 에셋을 월드 단위로 수명이 관리되는 월드 서브시스템의 UPROPERTY로 옮겼습니다. 같은 패턴이 다른 설정 클래스에 있는지도 확인했습니다(없었음). 재발을 막기 위해 트러블슈팅 문서에 항목을 남겼습니다.

**검토한 대안.** 대안 비교는 기록에 남아 있지 않습니다. 수정의 원칙은 "수명이 월드 단위로 관리되는 주인이 참조를 소유한다"입니다.

**검증.** 같은 조건(`-game -nullrhi` 런 맵, 적 30마리, 로비 이동 시 GC)에서 수정 전 빌드는 크래시가 재현되고 수정 빌드는 100초 동안 정상이었습니다. 일반·강제 유니티 빌드와 헤드리스 자동화 284건 중 283건 통과(실패 1건은 기존). 사용자의 패키지 재플레이는 당시 시점에 대기 중이었습니다.

**한계.** 재현은 렌더 없는 짧은 조건이었습니다. 100초 정상이 장시간 안정을 뜻하지 않습니다.

## 사례 2. 절벽 진입 시 슬라이딩이 끝나는 결함

**문제.** 2층 가장자리나 지면 끝으로 슬라이드하면 캐릭터가 멈췄습니다. 경계에 수직으로 진입하면 속도가 0이 되고, 45°로 진입하면 경계 옆으로 미끄러졌습니다. 진입 각도에 따라 달라지는 두 증상을 함께 설명할 원인이 필요했습니다.

**제약.** 슬라이드 속도 계산을 늘려서 증상을 덮는 방식은 피하고, 속도가 사라지는 최초 지점을 엔진 이동 경로에서 찾아야 했습니다. 프로젝트의 슬라이드는 엔진 CMC의 걷기 모드에서 앉기 상태를 사용하므로([01](01-movement-state-ownership.md)) 자체 슬라이드 계산뿐 아니라 엔진의 앉은 캐릭터 낙하 허용 조건도 적용됩니다.

**원인.** 엔진의 `bCanWalkOffLedgesWhenCrouching` 기본값이 false였습니다. 걷기 시뮬레이션이 앉은 캐릭터의 경계 이탈을 허용하지 않아 다음 경로를 탔습니다.

1. 경계에서 걸을 수 있는 바닥이 사라집니다.
2. `GetLedgeMove`가 경계를 따라 움직일 대안을 찾습니다. 수직 진입은 대안이 없고, 비스듬한 진입은 옆 이동이 가능합니다.
3. `CheckFall`도 낙하 허용 조건을 확인하므로 떨어지기 시작하지 않습니다.
4. 수직 진입의 실패 경로에서 `RevertMove`가 속도와 가속도를 0으로 만듭니다.
5. 다음 프레임의 슬라이드 방향 계산은 정규화할 속도를 잃고, 최소 속도 조건에 의해 슬라이드가 끝납니다.

두 증상은 같은 엔진 분기의 다른 결과였습니다. 슬라이드 코드에는 경계에서 떨어지는 처리가 이미 있었지만, 걷기 경로가 낙하 진입을 막아 그 처리에 도달하지 못했습니다.

**선택한 수정.** 이동 컴포넌트 생성자에서 앉은 상태의 경계 이탈을 허용했습니다. 새 예측 상태나 패킷 필드를 추가하지 않고 클라이언트·서버가 같은 기존 설정을 쓰게 합니다.

**검토한 대안과 기각 이유.** 슬라이드 중에만 낙하를 허용하는 재정의를 검토했습니다. 그러나 경계 직전에 슬라이드 시간이 끝나면 앉은 상태로 같은 문제에 다시 도달할 수 있었습니다. 앉아서 걸을 때도 경계를 넘으면 떨어지는 동작을 수용했으므로, 잔여 경로까지 기존 설정으로 정렬했습니다.

**검증.** 풀 리빌드 71액션 성공, 강제 유니티 빌드 통과, 자동화 58/58, 그리고 사용자 PIE에서 수직 슬라이드 낙하·45° 슬라이드 낙하·앉기 보행 낙하·서기 동작의 회귀 없음을 모두 확인했습니다.

**한계.** 당시 변경에 대한 검증이며 현재 이동의 모든 네트워크 조건을 새로 시험했다는 뜻이 아닙니다. 핵심은 기존 처리의 존재와 실제 도달 가능성을 구분하고 엔진의 상태 전환까지 추적해 수정 범위를 정한 과정입니다.

## 사례 3. 렌더 성능: 측정 위치를 바꿔 가며 GPU 52.7ms를 약 9.9ms로

**문제.** 사용자 PIE에서 숲과 바닥이 베이지색 체크무늬로 보이고 약 20fps였습니다. 로그에는 재질 사용 플래그 누락으로 "기본 재질을 쓴다"는 경고가 21건 있었습니다.

**제약.** 맵을 에디터에서 열면 플래그가 메모리에서만 켜져서, 그동안의 PIE와 측정은 정상으로 보였습니다. 한 세션의 측정으로는 원인이 보이지 않아, 같은 조건(무적, 시작 지점)에서 GPU 프로파일을 반복해야 했습니다.

**원인과 수정(1단계).** 프레임 차트로 GPU 병목이 98.7%였고 GPU 프로파일의 PrePass 18.7ms·BasePass 20.3ms·그림자 5.9ms가 큰 비중이었으며, Nanite 래스터화 삼각형이 거의 0이었습니다. Nanite 메시가 비-Nanite 대체 경로로 그려지고 있다는 뜻입니다. 묶음별로 숨겨 보는 실험은 효과가 작았습니다(다른 묶음이 화면을 채움). 원인은 재질에 두 사용 플래그(Nanite, 인스턴스드 스태틱 메시)가 한 번도 저장되지 않은 것이었고, 에디터에서 두 플래그를 켜 저장하자 **GPU 52.7ms → 16.5ms, 20fps → 55fps**, 경고 0이 되었습니다.

**2단계: 그림자.** 그림자는 7.0ms였고 그중 Nanite 그림자가 6.3ms(소프트웨어 래스터 4.3ms)였습니다. 같은 조건에서 각 설정을 한 번에 하나씩 바꿔 ProfileGPU를 두 번씩 쟀습니다(측정 잡음 ±1ms). 프로그래머블 래스터를 끄면 −0.9ms, 그림자 거리 배율 0.5는 −0.4ms, 캐스케이드 3장은 −1.8ms, 2장은 −2.3ms였습니다. 사용자의 결정으로 캐스케이드 4 → 3장, 그림자 거리 400m → 200m, 재질은 불투명으로 하고 일부 소실 연출은 데모에서 제외했습니다. 결과 **GPU 약 9.9ms, 86.5fps**(앞 단계 59fps, 처음 20fps), 그림자 2.8ms.

**검토한 대안.** 먼 곳의 그림자 품질을 얼마나 낮출지는 감각 판단이라 사용자 PIE로 남겼습니다. 캐스케이드 2장은 −2.3ms로 더 빨랐지만 사용자의 결정은 3장이었습니다.

**교훈.** 이전의 Masked 재질 비용 측정은 메인 뷰만 보아 그림자 캐스케이드 비용(+0.9ms)을 놓쳤습니다. 재질 블렌드를 바꿀 때는 그림자 깊이 패스도 함께 재야 합니다.

**한계.** 측정은 에디터 PIE 기준이고, 패키지 빌드에서의 확인과 먼 곳 그림자 품질의 사용자 확인은 남은 항목이었습니다. 측정 잡음이 ±1ms라 1ms 안팎의 차이는 구분되지 않습니다.

## 사례 4. 스웜 구조의 실측과 범위 축소

### 4-1. 2026-09 실측: 목표를 주장하지 않기 위한 측정

**문제.** 이전 단계는 다수의 적(1000+)을 스트레스 목표로 삼아 공유 길찾기 거리장과 정확한 클래스별 풀을 만들었습니다. 이 구조가 목표를 달성했는지 말하려면 조건이 고정된 측정이 필요했습니다.

**조건.** 같은 Development 패키지와 맵에서 솔로와 로컬 4인을 측정했습니다. Ryzen 7 7800X3D / RTX 4070 Ti, 1080p 렌더 호스트, Push Model(변경 속성을 명시하는 복제 방식) OFF였고, 4인 구성의 나머지 세 클라이언트는 **같은 PC에서 렌더 없이(nullrhi) 60fps로 실행**했습니다. 맵은 이후 폐기된 옛 맵입니다. P95는 프레임 시간의 95백분위 값입니다.

| 호스트 지표 | 솔로 | 로컬 4인 |
|---|---|---|
| 분석 창 / 평균 생존 적 | 76.3초 / 895 | 233.9초 / 891 |
| 평균 프레임 / P95 | 9.40ms / 12.17ms | 18.62ms / 24.93ms |
| 게임 스레드 / GPU | 9.39ms / 3.56ms | 18.57ms / 3.87ms |

**해석과 한계.** 평균 GPU 시간보다 게임 스레드 시간이 프레임 시간에 가까워 이 조건의 호스트 병목은 CPU였습니다. 일괄 처리 등을 포함한 Tickables는 4.95ms → 11.07ms, 서버 액터 복제는 0 → 1.51ms였습니다. 이 비교는 조사할 비용을 좁혀 줄 뿐, 인원 증가에 따른 원인을 하나로 분리한 실험이 아니고 최적화 전후도 아닙니다. 1000마리 소환 요청은 모두 전달됐지만 4인 분석 창의 생존 수는 829~956으로 감소했고 맵 하단 경계에 의한 회수가 44건 있었습니다. 따라서 **"1000마리 안정 유지 성능"으로 소개하지 않았습니다.** 두 분석 창의 이벤트 조건이 다르고 같은 PC 클라이언트의 CPU 부하가 섞입니다. 연결당 송신 약 41KB/s에서도 포화가 94% 프레임에서 기록되었고 원인은 미확정입니다. 원격 4인 환경은 별도 측정이 필요합니다.

### 4-2. 2026-11 범위 축소: 목표를 폐기하고 구조를 안전하게 지우기

**결정.** 2026-11의 범위 재정의([README](../README.md)) 과정에서 적 1000+ 목표를 폐기하고 범위를 줄였습니다. 스웜·표면 내비·지형·레이드 모드의 코드와 에셋을 지우는 묶음이었습니다.

**삭제의 규모.** 제품 파일 69개와 시험 파일 30개를 삭제했습니다. 이 밖에 플러그인과 스크립트, 쓰이지 않게 된 에셋 패키지도 정리했습니다.

**지우기의 위험과 제약.** 삭제는 지운 것만 영향을 주는 작업이 아니라 남은 코드가 암묵적으로 의존하던 것을 드러내는 작업입니다. 공용 계약(피해 계층·플레이어 이탈 처리)은 삭제 대상 안에 있어도 이식해 남겨야 했습니다. 목록이 닫혀 있다는 것을 먼저 증명한 뒤 지웠습니다.

**검증과 발견.** 단계마다 유니티 빌드, 고정된 시험 묶음(필터별 실행 수 대조), 흐름 스모크, 헤드리스 6개 맵 로드를 확인했고, **단독 컴파일로 숨은 include 3곳을 찾아 수리**했습니다. 지운 헤더가 다른 헤더의 선언을 대신 끌어오고 있었기 때문입니다. 쿠킹 결과를 삭제 전후로 비교해 빠진 항목이 삭제 대상과 보관 대상, 그것만 쓰던 에셋뿐임을 확인했고, 전체 자동화 634/634와 독립 구현 검토를 통과했습니다. 방 세이브 파일은 삭제 전후로 변하지 않음을 해시로 확인했습니다.

**얻은 규칙.** 삭제 묶음에서는 단독 컴파일이 숨은 전이 include를 잡습니다. 부분 빌드(`-skipbuild`) 패키지는 옛 타깃의 영수증을 써서 지운 플러그인 때문에 스테이징이 실패하므로 전체 빌드로 해소해야 합니다.

**한계.** 사람 플레이, 2인 접속, 프레임 시간, 패키지 실행은 이 묶음에서 확인하지 않았습니다. 삭제한 옛 보스 전투 경로는 시험이 없어 별도 후속 항목으로 남겼습니다. 이 범위 축소는 성능 개선이 아니며, 현재 단계에는 적 수 목표가 없습니다.
