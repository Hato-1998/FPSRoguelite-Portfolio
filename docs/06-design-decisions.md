# 설계 선택과 감수하는 비용

[← 포트폴리오](../README.md)

각 선택은 이 게임의 제약에 대한 답입니다. 적은 많고 플레이어는 최대 4명이며 전투는 계속되고 개인 빌드와 월드 교환은 같은 서버 상태를 공유합니다.

| 선택 | 제1원리 근거 | 엔진·기존 인프라와의 관계 | 대가·검증 |
|---|---|---|---|
| 공유 Flow Field | 소수 목표의 반복 탐색 공유 | 월드 베이크 기반 자체 표면 계산 | 개별 비용·동적 변화 한계 |
| 높이 레이어·역방향 낙하 | 겹친 바닥·단방향 이동 구분 | 배열 그래프·균일 비용 BFS | 레이어·베이크·연결 계약 |
| 정확한 클래스 풀 | 다른 종류 재사용 방지 | UE 액터 위에 클래스별 버킷 | 수요 불균형·재활성화 회귀 |
| 선택적 GAS | 스웜 개체당 반복 비용 최소화 | 특수 개체 GAS·일반 적 경량 체력 | 두 데미지 경로의 일관성 |
| 자산 정본·배치 거래 | 교환 실패 시 투자 보존 | UObject·액터 표현을 ledger로 조정 | 준비 피크·예약·복구 여유 |
| 서버 견적·재전송 영수증 | 조건 변경·중복 결제 방지 | 소유 객체 RPC에 revision·런 식별 추가 | 오래된 UI 거부·갱신 경험 |
| 이벤트 계보·작업 예산 | 빌드 연쇄 폭주 방지 | 전투 훅→값 이벤트→지연 executor | 지연·포화·공정성 |
| 수명·활성화 식별 | 재사용 대상의 오래된 효과 방지 | weak 참조에 별도 식별 추가 | 모든 지연 소비부 재검사 |
| CMC 예측 확장 | 이동 반응·서버 재현 유지 | SavedMove·기존 예측 사용 | 복원 상태·프록시 표현 |
| 정의·인스턴스·수치 분리 | 공유 콘텐츠·개인 투자 보존 | DataAsset·복제 입력·캐시 재사용 | 무효화·소비부 누락 |

Power를 성능 점수로 두는 성장 설계도 같은 원칙을 따릅니다. 실제 스탯의 성능을 비교해야 하므로 점수를 피해에 다시 곱하면 책임이 중복됩니다. 평가·역산 지원과 실제 생성기는 별도 단계입니다.

## 설명할 때 확인할 질문

- 목표에서 BFS를 시작하면 무엇을 재사용하며 낙하에 왜 유입 연결이 필요한가?
- 해시 버킷인데도 풀 취득 전체를 최악 O(1)이라고 할 수 없는 이유는 무엇인가?
- Reliable RPC가 있어도 서버 견적·요청·런 식별이 필요한 이유는 무엇인가?
- 최종 상태가 작은 교환에도 준비 순간의 메모리·액터 예산이 필요한 이유는 무엇인가?
- weak 참조가 유효한데 수명 식별이 다르면 왜 지연 효과를 버려야 하는가?
- 수식 시험 이후 실제 탄도·이동 소비부를 따로 확인해야 하는 이유는 무엇인가?
- 길찾기가 빨라도 전체 스웜 프레임이 느려질 수 있는 비용은 무엇인가?

설계 적합성, 코드 작성, 실행 결과와 성능 달성은 서로 다른 주장입니다.
