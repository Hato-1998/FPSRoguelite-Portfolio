# 설계 선택과 면접 설명 포인트

[← 포트폴리오](../README.md)

각 선택은 FPSR의 제약에 대한 답입니다. 모든 게임에 적용할 보편적인 정답으로 제시하지 않습니다.

| 선택 | 다른 선택과 비교 | 프로젝트에서의 이유 | 대가 |
|---|---|---|---|
| 공유 Flow Field | 적마다 독립 탐색 | 적은 많고 추적 대상은 소수 | 개별 경로 비용·행동의 자유도 제한 |
| 높이 레이어 | 순수 평면 그리드 / 일반 3D 탐색 | 겹친 바닥을 구분하면서 배열 기반 계산 유지 | 레이어 표현 한계와 베이크 계약 |
| 정확한 클래스 풀 | 한 배열 탐색 / 상속 허용 재사용 | 적 종류가 늘어도 다른 클래스 탐색을 피하고 타입 혼입 방지 | 클래스별 수요 불균형과 축출 정책 |
| 선택적 GAS | 모든 적에 ASC 부착 | 일반 적의 반복 비용을 낮추고 복잡한 능력은 특수 개체에 집중 | 경량 데미지와 GAS 경로의 일관성 관리 |
| 서버 revision 검사 | UI 상태를 신뢰 | 실시간 상태 변경과 중복 입력 대응 | 오래된 UI의 요청 거부 후 갱신 경험 필요 |
| 다형적 카드 효과 | 중앙 카드별 switch | 효과 종류 확장 시 중앙 적용 루프 변경 감소 | 효과별 사전조건과 콜백 계약 유지 |
| 무기 스탯 지연 계산 | 매 조회 재계산 / 결과 전체 복제 | 입력 변경 때만 재계산하고 동일한 계산 규칙 사용 | 무효화 경로 누락 시 오래된 캐시 위험 |

## 왜 기본 엔진 기능만으로 끝내지 않았는가

엔진의 UObject·Subsystem·Replication·GAS·Automation Framework를 기반으로 사용합니다. 그 위에서 공유 길찾기, 정확한 클래스별 풀, 거래 revision처럼 게임의 반복 비용이나 규칙을 표현하는 부분을 프로젝트 코드로 만듭니다. 엔진 전체를 대체하려는 설계가 아닙니다.

## 면접에서 코드와 함께 설명할 질문

- BFS를 목표에서 시작하면 무엇을 재사용할 수 있는가? 단방향 낙하에서는 왜 유입 링크가 필요한가?
- 클래스별 해시 버킷을 썼는데 왜 풀 취득의 최악 복잡도까지 O(1)이라고 할 수 없는가?
- Reliable RPC만으로 중복 구매를 막을 수 있는가? revision과 세션 검사가 각각 무엇을 해결하는가?
- `CanApply`와 `Apply`를 나눠도 부분 적용 문제가 남을 수 있는 조건은 무엇인가?
- 계산된 무기 스탯을 복제하는 대신 입력을 복제할 때 무엇을 얻고 어떤 무효화 경로를 유지해야 하는가?
- 적 1,000개에서 길찾기가 빨라도 전체 프레임이 느릴 수 있는 이유는 무엇인가?

답은 각 사례 문서와 실제 코드에서 찾아볼 수 있습니다. 실행 성능, 본인 기여 범위, 개발 기간처럼 추가 확인이 필요한 항목은 코드 구조의 설명과 구분합니다.
